# План реализации мультиязычности (i18n)

## Цель

Дать интерфейсу на минимум двух языках (**русский** и **английский**) без дублирования бизнес-логики: единый источник строк, предсказуемое поведение в Server Components, server actions и Telegram Mini App.

**Язык интерфейса берётся из данных Telegram** (язык клиента Telegram пользователя), а не из системных настроек браузера как основного источника. См. раздел ниже.

**Статус:** план к реализации.

## Текущее состояние

- Тексты **зашиты в компонентах** на русском (`app/`, `components/`), метаданные в `app/layout.tsx` на русском.
- Ошибки server actions: стабильные **`code`** в [[technical/error-code-catalog]] / `lib/errors/catalog.ts`, сообщения для toast частично с сервера — их нужно **маппить по коду + локали**, а не хранить только один язык в `message`.
- Даты: `date-fns` с `ru` в [[components/ui/date-picker]] — локаль календаря должна следовать выбранному языку.
- Отдельной библиотеки i18n **нет**; `next.config.ts` без `i18n`.

## Принципы

| Принцип                       | Смысл                                                                                                                             |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Ключи, не строки в коде**   | В коде — `t('group.settlements.title')`, не литералы длинных фраз                                                                 |
| **Один формат хранения**      | JSON/YAML-модули по локали (`messages/ru.json`, `messages/en.json`) или вложенные TS-объекты                                      |
| **Locale на стороне сервера** | RSC и серверные экшены должны знать текущую локаль при рендере и ответах                                                          |
| **Ошибки по `code`**          | Тексты для пользователя — из словаря `errors[code][locale]`, без локализации «сырых» `message` с бэка как единственного источника |
| **Язык из Telegram**          | Источник истины — `language_code` пользователя в Telegram; не подменять «автоматически» языком ОС без согласования продукта       |

## Источник языка: Telegram (обязательно)

Интерфейс должен соответствовать **языку приложения Telegram** пользователя (то, что задаётся в настройках клиента Telegram и отражается в данных пользователя Mini App).

1. **Клиент (Mini App):** в `Telegram.WebApp.initDataUnsafe.user` доступно поле **`language_code`** (строка вида `ru`, `en`, `de`, …). Его нужно маппить на **поддерживаемые локали** приложения (например только `ru` и `en`: для остальных — fallback на `en` или `ru` по правилам продукта).
2. **Сервер:** при разборе подписанного **`initData`** (уже есть поток авторизации через [[technical/auth-flow-telegram-nextjs]]) в JSON пользователя также есть **`language_code`**. После успешной валидации initData можно:
   - выставить cookie локали (`Set-Cookie`) в ответе API, чтобы **следующие** запросы RSC и server actions видели ту же локаль без задержки на клиент;
   - либо хранить предпочтение в сессии/профиле пользователя в БД (опционально, если нужна согласованность между устройствами вне Telegram).

3. **Не полагаться на `Accept-Language` как основной сигнал** для пользователей Mini App: он отражает браузер, а не выбор в Telegram. `Accept-Language` допустим как **fallback**, если приложение открыто **вне** Telegram (отладка в браузере) или `language_code` недоступен.

4. **Смена языка в Telegram:** при следующем открытии Mini App приходит обновлённый `language_code` — нужно **пересинхронизировать** cookie/хранилище локали (перезапись при совпадении сессии).

Отдельный UI «выбор языка внутри приложения» в плане не обязателен; если появится, он должен **переопределять** только до следующего входа из Telegram или явно сохраняться как пользовательское исключение (продуктовое решение).

## Выбор стратегии: где хранить локаль

### Вариант A — префикс в URL (`/ru/...`, `/en/...`)

- **Плюсы:** SEO, явный шаринг, стандарт для Next.js + middleware.
- **Минусы:** все ссылки и `Link`/`redirect` с префиксом; ссылки из Telegram-бота должны включать локаль или редирект с дефолта.

### Вариант B — без смены пути (cookie `NEXT_LOCALE` или заголовок)

- **Плюсы:** стабильные URL для Mini App и deep links; проще миграция существующих маршрутов.
- **Минусы:** хуже для SEO (если публичный сайт важен); нужно читать cookie в middleware и прокидывать locale в серверные компоненты.

### Вариант C — гибрид

- Дефолтный язык без префикса, остальные с префиксом — усложняет роутинг.

**Рекомендация для Money Split:** начать с **варианта B** (cookie, заполняемая из **Telegram `language_code`**), если приоритет — **Mini App и одинаковые URL**; перейти на **вариант A**, если позже понадобится SEO и явные локализованные URL. Cookie в варианте B — **технический перенос** выбранной из Telegram локали на HTTP-запросы, а не независимый выбор языка. План ниже описывает шаги так, чтобы **библиотека словарей** не зависела от выбора A/B.

## Рекомендуемый стек (Next.js App Router)

- **`next-intl`** — проверенная связка с App Router, `useTranslations`, `getTranslations` в RSC, плюс опционально middleware для `[locale]` или кастомный провайдер через cookie.
- Альтернативы: **Paraglide**, **typesafe-i18n** — сильнее типизация, выше порог входа.

Пакет и версию зафиксировать при внедрении по документации Next 16 / совместимости.

## Структура проекта (ориентир)

```
messages/
  ru.json
  en.json
lib/
  i18n.ts              # конфиг локалей, defaultLocale, список supported
```

- Вложенные ключи по смыслу: `common.save`, `group.settlements.title`, `errors.FORBIDDEN_GROUP_ACCESS`.
- Для **длинных** фраз с переменными — ICU-плейсхолдеры или `{name}` согласно выбранной библиотеке.

## Слои, которые нужно пройти

### 1) Корневой layout и метаданные

- `generateMetadata`/`metadata` с `title`/`description` по локали.
- Атрибут `<html lang="...">` из текущей локали.

### 2) Страницы и компоненты

- Server Components: `getTranslations('namespace')` (или аналог).
- Client Components: `useTranslations('namespace')`.
- Постепенная миграция: сначала **общие** (`common`, `nav`), затем **группы** и **траты**, затем редкие экраны.

### 3) Server actions и API

- Не возвращать пользователю финальный текст ошибки на одном языке из глубины стека; возвращать **`code`** + опционально параметры; на клиенте `t('errors.' + code)` или централизованный маппер в [[lib/errors/user-hint]].
- Валидация Zod: вынести сообщения в функции, принимающие `t`, или использовать **общий словарь** для `z.string().min(1, { message: t('...') })` на клиенте; на сервере — либо ключи ошибок, либо серверный `t` при известной локали (передавать `locale` в action).

### 4) Форматирование чисел и денег

- [[technical/money-formatting-policy]]: для отображения использовать `Intl.NumberFormat(locale)` там, где нужны разделители и валюта.
- Для `date-fns`: подключать `ru` / `en` в календаре и date picker в зависимости от локали.

### 5) Toasts (Sonner)

- Все строки в `toast.success/error` — через `t()` на клиенте или прокинутые уже переведённые строки из сервера (если сервер знает locale).

### 6) Тестирование

- Smoke: смена **языка в настройках Telegram**, повторное открытие Mini App, создание группы/траты — ожидаемый язык интерфейса.
- Отладка в браузере вне Telegram: поведение fallback (`Accept-Language` / дефолт).
- Регрессия: форматы денег и дат в RU и EN — по [[technical/money-formatting-policy]].

## Порядок внедрения (фазы)

1. **Инфраструктура:** зависимость, конфиг локалей, провайдер (или middleware), cookie; **запись локали из `language_code`** при авторизации initData и/или в `WebAppProvider` при монтировании; чтение locale в RSC.
2. **Словари:** вынести строки из `layout`, home, навигации; выставить `lang` из текущей локали.
3. **Ошибки:** маппинг `ActionErrorCode` → ключи i18n; обновить `actionErrorHint` и места вызова toast.
4. **Группы и траты:** крупные формы и карточки.
5. **Остатки:** второстепенные экраны, aria-label, пустые состояния.
6. **Полировка:** копирайт EN, единообразие терминов (settlement, split, expense).

## Риски и ограничения

- **Объём строк:** первый проход займёт время; имеет смысл **скриптом** найти кириллицу в `tsx` для контроля покрытия.
- **Дублирование:** один термин — один ключ (`common.back` вместо трёх вариантов «Назад»).
- **Server actions без locale:** при передаче только `FormData` без cookie — явно передавать `locale` в hidden field или заголовок из клиента (если библиотека не подхватывает автоматически).
- **Расхождение cookie и Telegram:** если пользователь сменил язык в Telegram, а cookie старая — до следующей синхронизации возможен неверный язык; mitigations: обновлять cookie при каждом успешном `initData` / при монтировании WebApp.

## Чеклист реализации

1. Зафиксировать список локалей (`ru`, `en`), таблицу **`language_code` → locale**, стратегию URL (A или B).
2. Установить и настроить `next-intl` (или выбранный аналог), `lib/i18n.ts`, каталог `messages/`.
3. Реализовать **синхронизацию локали с Telegram:** чтение `language_code` на клиенте и/или из разобранного `initData` на сервере; cookie / сессия; middleware применяет локаль к запросу.
4. Обновить `layout`/`metadata` и корневые страницы.
5. Централизовать тексты ошибок по `ActionErrorCode` + локаль.
6. Пройти формы и `zod` с сообщениями из словаря (поэтапно).
7. Локализовать `date-fns`/календарь под локаль.
8. Прогнать ручной чеклист по [[technical/mvp-test-plan]] на двух языках (при необходимости расширить план тестов).
